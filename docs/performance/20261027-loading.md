# Performance Audit / Optimization Report

App: KC CuTo CRM — https://kc-cuto.kaicomhub.com/  
Baseline: 249e00afd2817c555a12d9c0e68c9d3992776537  
Date: 2026-10-27, Asia/Bangkok. Scope: frontend read RPC transport and form lookup loading. Shared Supabase-Tech Savvy database inspected read-only; no schema/data mutations.

## 1. Executive summary
CONFIRMED: six read-only RPCs used the SDK's default POST. The existing REST policy treats POST as a mutation and clears cached reads both before and after the call. This needlessly invalidates warm data and queued reads. Separately, form initialization awaited eight independent lookups sequentially.

Changed only audited read calls to the documented `rpc(name,args,{get:true})` form. Existing deduplication, 60-second cache, per-user headers, access invalidation, backoff and five-read gate now apply. Actual writes/approvals keep their original transport and bypass the read queue. Independent form lookups start together; editing opens only after required results succeed.

## 2. Traced flow
Create/edit form → internal-workspace.start → quotations/prices/templates/relations/master data → Supabase REST policy → existing permission-checked SQL → Lookup/Masters/Edit. Company branding, inventory catalog, assignment directories and access context use the same read path. No SQL definitions, grants, RLS or document calculations were changed.
